## Material alternatives

- **How to represent "every card row for the id" in the view model.** Considered reusing `explorer.models.ResultItem`/`CardRow` unchanged and doing all open-link and mode-labelling logic in the Jinja template. Rejected: Jinja has no clean way to call a Python helper with the per-row mode-effective/line-number context without registering global filters the integrator would then own; instead this module defines its own thin wrapper dataclasses (`CardLine`, `ResultView`, `IdentifierRow`) that carry a precomputed `open_link` per card row, keeping every URL-construction decision in one tested Python function (`_open_link`) rather than scattered across template conditionals.
- **Open-link line anchor when several card rows share one doc_id.** The dispatch specifies the link shape per *mode* ("lexical hits link to `/doc/<card_ref>?line=<line_no>`, other modes to `/doc/<card_ref>`") but a shared-id result (hand + amendment) has one `line_no` from the evidence and several card rows, each with its own `card_ref`. Considered attaching the line anchor only to whichever card's `doc_ref` happens to equal the FTS match's `path`. Rejected as needlessly fragile (silent mismatch keeps growing every time a document is renamed) in favor of the simpler rule actually implemented: every card row sharing the id gets the same `?line=<line_no>` hint, mode-gated, never row-gated -- consistent with O7's "never pick one row silently" and cheap to state precisely in code (`_card_line` takes one `line_no` for the whole item).
- **Narrowing match rule across several card rows.** Considered requiring every card row of an id to satisfy the narrowing filters (AND across rows). Rejected: a hand and its amendment can differ in `status` even while sharing a `doc_type`, and requiring all rows to match would make narrowing silently drop an id whenever any one of its rows happened to disagree, which is a worse failure mode than the implemented rule (an id survives narrowing if *any* one of its rows satisfies every supplied filter, `_item_matches_narrow`) -- consistent with treating narrowing as "does this id belong under the current lens," not "do all its historical variants."
- **Fake-adapter design for the vector-available path.** Considered building a full stand-in that also implements `resolve_identifier`/`cards_for_doc_id` realistically. Rejected as unnecessary: those two methods are never called by `run_search` on the hybrid/graph paths (the adapter's own `search_hybrid`/`search_graph` already bake `exact_identifier_match` into each item's `Evidence`, verified by reading `explorer/corpus_adapter/adapter.py`'s `_items_from_doc_ids`), so `FakeAvailableAdapter` stubs them to empty/`None` and documents why in a comment, keeping the fake's surface exactly as large as what `run_search` actually touches.
- **Live-smoke guard fixture scope.** Considered an autouse, session-scoped guard (mirroring `tests/corpus_adapter/conftest.py` literally) so every test in the directory is wrapped. Rejected: every other test in this module runs against the fixture index, and forcing a live `CorpusAdapter` construction (with its `isfile` check and `RHACO_corpus_index` import) at the start and end of every session run for tests that never touch the live index adds an unrelated dependency edge for no assertion benefit. Implemented instead as a plain (non-autouse) fixture that only the one live-smoke test requests -- same technique (`corpus_cards_sha` + mtime, a fresh adapter instance for the "after" read to defeat the 5 s cache), narrower blast radius.

## Decisions

- `run_search`'s `settings` parameter is accepted but unused (`del settings` with a docstring note) -- kept for contract symmetry with the dispatch's literal signature (`run_search(adapter, settings, query: dict) -> SearchView`); nothing about search is configurable beyond the query string today (CONSTRAINTS.md S7).
- `data-vector` is rendered on every mode, including `identifier` and `lexical` (which never depend on the vector channel for their own retrieval) -- read literally from deliverable 3's `<html data-mode="..." data-vector="available|unavailable">` line, which does not gate `data-vector` on mode the way the general A19 convention note ("where it applies") does. `adapter.vector_availability()` is cached <= 5 s by the adapter (ARCHITECTURE.md A9), so this costs at most one cheap cached call per request regardless of mode.
- The `Evidence` "lexical excerpt, not the hybrid evidence" label is used verbatim for both `hybrid`/`hybrid-degraded-lexical` and `graph`/`graph-degraded` items with `excerpt_source == "lexical-lookup"`, matching the dispatch's literal wording, which groups hybrid and graph under one label even though the label mentions "hybrid" specifically.
- Identifier-mode rows carry no `Evidence` disclosure. The dispatch's evidence-disclosure deliverable (item 2) and its test checklist (item 5) both describe "Why this result" only for lexical/hybrid/graph results; an exact-alias match is self-evidently "exact" with nothing to disclose beyond the id itself, so identifier rows render only the id and its card rows.
- `narrow_doc_type` / `narrow_status` / `narrow_lifecycle_state` / `narrow_program` are accepted as query parameters on every mode's request but are only ever applied inside `_run_hybrid_or_graph` -- an identifier or lexical request that happens to carry a `narrow_*` parameter silently ignores it (O5: narrowing is a hybrid/graph-only post-hoc control, never retrieval-side, and lexical already has its own retrieval-side filters).
