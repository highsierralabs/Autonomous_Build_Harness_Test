## Material alternatives

- **Where "direction" comes from for a rendered edge.** Considered recomputing `direction` from `edge.from_id == center.doc_id` (or `== center.filename_stem`) independently in the lineage service, mirroring how a naive reader might. Rejected: under `reverse_edges`, the adapter swaps `from_id`/`to_id` but this module never sees which side was "originally" which -- recomputing direction from the (already swapped) ids would just re-derive the SAME bucket the adapter chose, so it changes nothing when the fault is off, but reads as fragile and invites a future edit that "fixes" it into re-normalising the fault away. Chose instead to carry `direction` as a plain field set once, at the point each `LineageEdgeView` is built from a specific `EdgeSet.outgoing`/`.incoming`/`.unresolved` list -- literally "whichever bucket this came from," which is both simpler and is what the KB3 contract in the dispatch requires ("must reflect the adapter's returned from/to exactly").
- **hops=2 direction semantics and relation-filter interaction.** Neither `ARCHITECTURE.md` nor the dispatch fully specifies what "direction" means for an edge discovered two hops out (it does not touch the center at all), or whether the relation filter should also gate hop-2 expansion. Considered (a) leaving hop-2 edges unfiltered and un-labelled by direction; (b) computing a "relative to center" direction via a graph-distance heuristic. Chose: `direction` for a hop-2 edge is relative to the hop-1 neighbour whose own `edges_for` produced it (the same "whichever bucket" rule, applied one level out), and the relation filter is applied at both hops -- a filtered view only ever grows along the filtered relation. This is a disclosed design decision, not a specified contract; **no acceptance test in the dispatch exercises `hops=2` behavior**, so this path is exercised only by the ad hoc no-crash check (Evidence #16), not a committed assertion.
- **Node-cap (200) enforcement point.** Considered capping after collecting everything (simpler code, wasted adapter calls past the cap). Chose to check the cap before each new card is added and to stop hop-2 expansion early once it bites, mirroring the adapter's own `Subtree.truncated` style (`len(rows) >= max_results`). The fixture has 7 cards total, so this path is UNVERIFIED beyond code inspection -- no test reaches 200 nodes.
- **Graph layout as a separate, non-serialized structure.** Considered adding `x`/`y` fields directly onto `LineageEdgeView`/a node view inside `LineageView`, so the API twin would carry pixel geometry too. Rejected: the API's stated purpose is data parity with the page ("carrying the center card, every edge as {...}, the supersession chain..., the campaign subtree, the active relation filter and hops") -- pixel coordinates are presentation, not data, and including them would make the JSON twin's shape depend on an arbitrary viewBox size. `compute_layout(view)` is called only by the HTML route in `routes.py`; `/api/lineage/...` never touches it.
- **Typed-edges narrative section vs. graph-only rendering.** The dispatch's deliverable #1 describes "the typed edges from `adapter.edges_for(center)`: outgoing, incoming and unresolved, each rendered directionally" as distinct from the graph and the reasoning trail. Rather than relying on the SVG alone to carry this, the template renders a separate plain `<ul>` per bucket (each `<li>` carrying the same `data-relation`/`data-edge-from`/`data-edge-to`/`data-edge-direction` attributes as the graph's `<line>` elements) so the same contract is checkable from plain markup and is fully legible with JavaScript disabled (the module's own added rule) without depending on SVG traversal.

## Decisions

- `relation_options` (the filter control's choices, with counts) are always computed from the center's own **hop-1, unfiltered** edge set ("the relations actually present around the center") -- unaffected by the current `relation` filter (so switching filters is always possible) and unaffected by `hops` (so the control does not change shape as the graph expands).
- The "no recorded relationships" state and the filter-independent "has_relationships" flag are both computed from the center's unfiltered hop-1 `EdgeSet`, so a relation filter that narrows everything to zero rows is shown as "no results for this filter," never as "no recorded relationships" -- the fixture does not have a case that distinguishes these two states, so only the true-zero-edges path (the EVT card) is exercised by a committed test; the filtered-to-zero path is implemented (the typed-edges lists and graph would simply render empty under `view.has_relationships == True`) but UNVERIFIED by an automated test this round.
- `target_card_refs` (the API contract's named field) is populated as `to_card_refs` for an `outgoing` edge and `from_card_refs` for an `incoming` edge -- "the other side from the anchor," matching the reader module's existing `target_cards`/`source_cards` convention (`explorer/reader/service.py`'s `_lineage_links`) rather than inventing a new one.
- `Edge.direction_label` is used verbatim, never re-derived per direction (dispatch: "do not re-derive labels") -- unlike the reader module, which hand-overrides the `supersedes` label for its incoming case (`_supersedes_narrative`). This means an incoming `supersedes` edge on this page is labelled "is superseded by" even when read from the *superseding* document's own page, which reads awkwardly in that one case but is the literal, explicit instruction for this module; the `direction` attribute (outgoing/incoming/unresolved) is what disambiguates it, not the label.
- The amends edge's `from_id` (the amendment's own filename stem, O8) is never resolved to a real `CardRow` through `adapter.cards_for_doc_id` when the edge is viewed from the **incoming** side (see "Unresolved uncertainty" below) -- rather than working around this in the lineage module (which would mean either re-deriving a lookup the adapter does not expose, or silently guessing), the literal id is shown as plain, unlinked text, matching "never infer a relationship not recorded" and "render the literal id" for anything the adapter cannot resolve.

## Unresolved uncertainty

- **`CorpusAdapter.edges_for`'s `source_cards` cannot resolve an `amends` edge's `from_id` when it is a filename stem, not a doc_id.** Verified directly against the adapter (fixture index): for the HND parent's incoming `amends` edge (`from_id="RHACO-HND-20260115-003_Fixture_Handoff_Amendment_A1"`), `edge.source_cards == []` and `adapter.cards_for_doc_id(edge.from_id) == []`, because `_cards_for_doc_id` queries `WHERE doc_id = ?` and the amendment's OWN doc_id is the shared parent id, not its own stem -- the stem is never anyone's `doc_id`. Consequence: on a parent card's own lineage page, the incoming `amends` edge shows its source as literal, unlinked text (no `<a>`, no `data-card-ref`) rather than a working link to the amendment document, even though the amendment card is indexed and resolvable by `card_ref`. This is a pre-existing adapter behavior (not introduced by this round -- confirmed unaffected by any lineage-owned code) and is filed as a Change request below rather than worked around in this module.
- **An amendment's own `amends` edge is double-classified by the adapter** into both `outgoing` and `incoming` on the amendment's own lineage page: `edges_for`'s two independent `if` checks (`from_id in (doc_id, stem)` and `to_id in (doc_id, stem)`, `explorer/corpus_adapter/adapter.py` lines 513-516) are not mutually exclusive, and for the amendment's own `amends` edge (`from_id` = its own stem, `to_id` = the shared doc_id) BOTH conditions are true when viewed from the amendment's own card (whose "identity" is exactly `{doc_id, stem}`). Verified: `GET /lineage/<amendment-card-ref>` shows the same `amends` edge once under "Outgoing" and once under "Incoming" with identical `from_id`/`to_id`. No task-B8 acceptance test checks for absence of this duplicate (only presence of the outgoing instance, which the committed test asserts), so this is disclosed here rather than papered over.
- **hops=2 has no committed regression test** (see "Material alternatives"); it is exercised only by an ad hoc, non-committed script during this round (Evidence #16) confirming no crash across all 7 fixture cards, not correctness of its direction/relation-filter semantics.
- **The 200-node graph cap is untested at the cap boundary** -- the fixture has 7 cards; the cap logic is implemented and code-reviewed but its `truncated` flag has never actually flipped true in any run this round.

## Change requests

- **Requestor:** lineage (B8). **Affected contract/path:** `explorer/corpus_adapter/adapter.py`, `CorpusAdapter.edges_for` (the `edge.source_cards = self._cards_for_doc_id(conn, edge.from_id)` / `edge.target_cards = self._cards_for_doc_id(conn, edge.to_id)` lines). **Change:** when an edge's `relation == "amends"`, the side holding a filename stem (`from_id` per O8) should resolve to its own `CardRow` via a stem-aware lookup (e.g. `WHERE doc_filename LIKE stem || '.%'`, or a new documented query keyed on `doc_filename`) rather than `cards_for_doc_id`, which only matches `doc_id` and returns nothing for a stem. **Evidence:** this round's report, "Unresolved uncertainty" above -- reproduced directly against the fixture adapter (`edge.source_cards == []`, `cards_for_doc_id(stem) == []`) for the HND parent's incoming `amends` edge. **Compatibility impact:** additive only -- `source_cards`/`target_cards` for every other relation is unaffected; only the currently-empty `amends`-from-stem case would start returning a populated list. **Migration:** none (no caller currently depends on this list being empty). **Invalidated tests/probes:** none identified; `tests/corpus_adapter/test_lineage.py`'s existing amendment test only checks `edge_set.outgoing`'s `from_id`, not `source_cards`, so it would still pass; this module's own `test_hnd_page_incoming_campaign_child_and_amends` asserts only the literal id text (not a link), so it would also still pass once the caller side is a link -- no test would need to change, only gain coverage.

## Assumptions

- An unrecognised `?relation=` value (not one of `cites`/`supersedes`/`amends`/`campaign_child`) is treated as "no filter" (falls back to showing every relation), never a 400 -- consistent with the codebase's existing pattern of silently falling back to a default on an unrecognised query parameter (e.g. `explorer/corpus_adapter/sql.py`'s `parse_sort`).
- An unrecognised `?hops=` value (anything other than the literal `"2"`) falls back to `1`, for the same reason.
- The reasoning trail's stable sort key is `(date is None, date, card_ref)` -- undated cards last, ties (including same-date cards) broken by `card_ref` for determinism across runs, since `CardRow.date` alone is not guaranteed unique.
- `relation_options`' display order follows the fixed `KNOWN_RELATIONS` tuple order (`cites, supersedes, amends, campaign_child`) rather than count-descending or alphabetical, so the control's shape is stable across requests to the same center.
