## Material alternatives

- **How to mark the active nav item (task item 1, bullet 2).** Considered a new `{% block nav_active %}{% endblock %}` that every consuming template would need to override with its own page-key string. Rejected in favor of deriving it from `request.url.path` (Evidence #3): every route already builds its `TemplateResponse` the same way, so this is genuinely "an existing hook" rather than a new contract surface, it required zero changes to any other module's template, and the "prove every existing template still renders unchanged" burden the dispatch attaches to the new-block option does not apply.
- **Row selector for keyboard navigation (task item 3).** ARCHITECTURE.md A19 and task item 55 both define rows as "exactly the elements carrying `data-doc-id`." Considered a narrower, per-page allowlist (e.g. `tr[data-doc-id], li.result-card, li.identifier-results > li`) to exclude the reader's inline dependency/supersession links, which also carry `data-doc-id` but are prose references, not list rows. Rejected: the dispatch's definition is explicit and literal, and guessing which `data-doc-id` elements "really" count as rows would be an uninvited judgment call about markup I do not own (see "Unresolved uncertainty").
- **Authority-notice robustness (task item 1, bullet 3).** Considered (a) keeping `.split('. ', 1)[1]` (rejected -- exactly the fragility named in the dispatch: breaks if the sentence's first full stop moves or a `. ` appears earlier); (b) a regex; (c) editing `explorer/models.py` to expose lead/rest separately (blocked -- not an owned path, and not needed). Implemented `startswith` + a length-based slice with a safe fallback to the unbolded whole string, verified in isolation (Evidence #4).
- **`.frozen`/`.frozen-marker` treatment.** Considered keeping the round-0 seed's plain small-caps grey text. Upgraded to a bordered warn-toned badge (still text-first: the word "frozen" is never removed) for a stronger at-a-glance signal, consistent with `.degradation`'s existing warn palette.
- **Keyboard-selection visibility.** Considered relying on native `:focus` by adding `tabindex` to every row. Rejected: that would require editing `catalog.html`/`search.html` markup I do not own, for elements (`<tr>`, nested `<li>`) that are not naturally interactive; a script-applied CSS class plus an `aria-live` announcement achieves the same visibility and screen-reader exposure without touching any other module's template.
- **Lineage's wide-content `<svg>` container (task item 2, bullet 2).** The lineage module is being built concurrently in a separate worktree and is not present here; no consuming markup exists to verify against. Deferred to the lineage builder's own module CSS (the same ownership boundary that keeps `.table-scroll`/`.source-scroll` inside `catalog.css`/`reader.css` rather than here) instead of guessing a class name preemptively.

## Assumptions

- The dispatch's "aria-current on exactly the active one" requirement (task item 4, bullet 1) was read as a requirement about the four specific URLs it lists, not as a claim covering every conceivable future route shape (see "Unresolved uncertainty").
- No test was written asserting the presence of the `prefers-reduced-motion` or `@media print` rules in `app.css`; both are disclosed as UNVERIFIED-by-test behavior (a file-content grep would only prove the rule text exists, not that it changes rendering, so it was not added merely to inflate the count of green assertions).
